# 版本与变更管理规范

## 版本号

应用版本使用 `主版本.次版本.修订号[-预发布标识][+构建号]`，例如 `0.1.0+1`。`pubspec.yaml` 是构建版本的唯一来源；`AppConstants.version` 不含 `+构建号`，只用于 UI 展示，二者必须同步。

- `0.1.0-beta.N`：公开测试版本；每个 beta 必须经过完整测试和 Windows Release 构建验收。
- `0.1.0`：首个稳定版本；本轮将 Windows x64 安装器作为正式发布产物。
- `0.x.y`：尚未承诺稳定兼容；改动仍需记录，但不按固定“功能阶段”机械映射版本。
- `+N`：构建标识；每次可下载构建递增，不替代产品版本。

当前代码版本：`0.1.0+1`。这是首个稳定版本的本地构建版本；公开发布前仍需完成本轮 Release 安装器和冒烟验证。

## 每轮变更必做

1. 修改 `pubspec.yaml` 版本时同步 `lib/shared/constants.dart`。
2. 在 [变更记录](变更记录.md) 顶部追加记录，并更新文件顶部的版本索引。
3. 更新 [项目进度交接](项目进度交接.md)：实现路径、验证结果、已知问题、接手工作。
4. 影响架构、平台边界、依赖或用户操作时同步架构/README/专题文档。
5. 运行与影响匹配的格式检查、分析、测试和构建；文档要区分通过与未通过。

具体交付清单见根目录 [AGENTS.md](../AGENTS.md) 与 [文档维护规范](文档维护规范.md)。

## Git 使用约定

每个提交尽量保持单一主题，使用清晰的中文或英文描述，例如：

```text
[player] Fix lyrics translation timing
[docs] Prepare 0.1.0 beta handoff
```

当前工作区是否含 Git 元数据应以 `Test-Path .git` / `git status` 现场检查为准；不要假设仓库已初始化、存在远端或已有基线。初始化 Git、创建远端、提交或推送均应由维护者决定。

需要回退时先看 `git status` 和 `git diff`，保存未提交修改，再选择 `git revert`（共享历史）或 `git restore -- <明确文件>`（丢弃指定工作区改动）。禁止未经确认使用会覆盖整棵工作区的重置命令。

## 发布标签与清单

Git 仓库建立且通过发布门槛后再创建标签，例如：

```powershell
git tag -a v0.1.0 -m "HoH music 0.1.0"
```

发布包必须至少包含版本、平台/架构、构建时间、许可证/NOTICE、已知限制和校验值。依赖锁定于 `pubspec.lock`；升级依赖时检查 [开源项目与协议清单](开源项目与协议清单.md)，不要忽略或删除锁文件。
