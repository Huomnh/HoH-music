# 文档维护规范

本规范适用于所有参与 HoH music 的 agent 和开发者。文档不是代码完成后的可选收尾，而是交付的一部分；交接记录尤其重要，因为下一位接手者不应依赖聊天历史。

## 每次代码任务的必做核对

- **项目进度交接**：在 `docs/项目进度交接.md` 顶部更新“最后更新”版本和平台阶段，并新增本轮摘要。写清功能行为、关键文件/入口、验证结果、已知限制和合理的后续工作。
- **变更记录**：在 `docs/变更记录.md` 文件顶部记录用户可见变化和实现位置，并同步版本索引表。版本号必须遵循 `docs/版本控制规范.md`；纯文档整理无需虚增产品版本。
- **架构文档**：当数据流、模块职责、跨平台边界、持久化格式、协议或设计决策变化时，同步 `音乐播放器架构文档.md`。不要把方案或计划写成已实现事实。
- **README / 专题文档**：当功能入口、当前版本、构建步骤、用户使用方式或专题契约发生变化时同步对应文档；检查已有表述，清除与当前实现冲突的说明。
- **验证**：按改动风险运行分析、测试或构建；文档中准确区分“已验证”“未验证”“受环境限制”，不得把计划中的验证写成通过。

## 交接条目模板

```md
### 本轮 <主题>（<版本>）

- 行为/结果：<用户现在能看到或做到什么>
- 实现位置：`path/to/file` — <职责或关键入口>
- 验证：<命令及结果>
- 限制/后续：<没有则写“无”>
```

## 完成前复核

1. 搜索本轮主题词和版本号，确认交接文档、变更记录、版本索引及受影响专题文档都已更新。
2. 检查链接仍指向有效路径，术语、默认行为和代码实际一致。
3. 明确保留工作区中用户已有的改动；文档核对只针对本轮范围，不覆盖无关内容。
4. 最终回复简要列出更新了哪些文档和验证结果，不能用回复代替仓库中的记录。

## 文档职责

| 文档 | 主要读者 | 记录内容 |
|---|---|---|
| `docs/项目进度交接.md` | 下一位 agent / 维护者 | 当前状态、近期决策、验证、限制、接手入口 |
| `docs/变更记录.md` | 开发者与用户 | 每次版本变更、文件影响、版本索引 |
| `音乐播放器架构文档.md` | 实现者与架构评审者 | 稳定模块边界、数据流、平台策略 |
| `README.md` | 使用者与贡献者 | 项目简介、当前能力、入门和构建入口 |
| `docs/*专题*.md` | 对应模块维护者 | 协议、平台、构建、性能等专项细节 |
